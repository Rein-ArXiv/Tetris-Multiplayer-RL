# 2026-09-19 구조·유지보수·문서·출시 품질 검토와 수정

## 판단과 검토 범위

계정 보관·화면·HTTP·OS 경로를 분리하고, 두 relay가 하나의 서버 경기 검증기를 쓰도록
수정했다. 발견한 허위 결과 지급 경로와 JSON 문법 검사, 주요 사용자 오인 흐름은 코드와
회귀 검사로 보강했다. 콘텐츠 진입점과 관련 Part도 갱신했다.

다만 main과 reactor의 책임이 모두 작게 분리된 것은 아니다. SOLID를 완전히 준수하거나
공개 경쟁 서비스의 모든 어뷰징을 막았다고 판정하지 않는다. 특히 정상 규칙으로 일부러
지는 담합·다중 계정·자동 플레이는 서버 시뮬레이션만으로 해결되지 않는다.

기준은 `3cd7b73` 뒤에 추가한 계정·품질 변경이다. 이 문서는 해당 코드와 함께 버전 관리한다. 실제 운영 데이터·설정을 바꾸지 않았다. 검사는 임시
DB·사용자 폴더·loopback 서버에서 수행한다. 공개 인터넷 침투 시험, Windows/macOS
실기기 UI·배포 확인, 신규 담당자의 온보딩 실험을 완료했다는 의미는 아니다.

### 서버 결과 검증의 의미

이전에는 요약끼리 모순되지 않는지를 확인했다. 현재는 요약을 종료 요청으로만 사용하며
승패·점수·줄 수·경기 시간은 서버의 입력 시뮬레이션에서 가져온다. 입력 마스크·길이·연속성·
재전송 일치·최대 틱·벽시계 대비 선행량을 검사한다. 채널당 기록과 처리 범위도 제한한다.

thread relay는 `sumMu`, reactor는 채널 소유 loop로 검증 상태를 보호한다. HTTP 저장은
이 상태 소유 경계 밖에서 실행한다. 같은 `server/ranked_game.h`를 사용하므로 보상 정책의
핵심이 두 파일에서 서로 달라지는 위험을 줄였다. DB의 UUID 멱등성은 그대로 유지한다.

연결이 끊겨도 종료 입력을 모두 받은 경기라면 기록한다. 반대로 한쪽의 승리 신고만 있거나
아직 보드가 종료되지 않은 경기는 지급하지 않는다. 따라서 패배 직전 이탈로 기록을 피하는
행위를 제재하는 정책은 남는다. 보상 방어와 몰수패·제재 정책을 혼동하지 않는다.

### 계정의 파일 손상과 저장 실패

키·backup·pending 중 하나라도 다른 서버 소유거나 손상됐으면 변경 전 중단한다. 폴더
locator의 짧은 해시가 일치하더라도 전체 origin 확인 없이 비밀을 읽거나 덮지 않는다.
옛 무소속 token은 화면에 표시한 서버로 가져오는 명시적 동작에서만 전송한다.

서버 변경 후 로컬 저장 실패에는 pending이 남고 같은 요청으로 재시도한다. 서버가 이미
성공했어도 키를 두 번 교체하지 않는다. 최초 guest 저장 실패의 Retry는 guest를 새로
발급하지 않고 메모리의 같은 키를 저장한다. 화면·서비스·파일 경계를 나눠 이 두 실패를
서로 다른 흐름으로 설명하고 검사할 수 있게 했다.

## 가독성과 SOLID

`SimGame`은 계속 렌더러·오디오·I/O 없이 규칙만 소유한다. 같은 코어가 클라이언트,
Python 학습, 봇 재현, PvP 서버 판정에 쓰인다. `presentation`과 캐릭터 설정은 규칙 변경
없이 외형 콘텐츠를 확장하는 경계다. 이 강점은 유지했다.

새 계정 코드·파일 교체·DB 마이그레이션의 압축된 한 줄 표현을 풀어 쓰고, 소유권·원자성·
실패 후 보존 이유를 주석으로 남겼다. 상점의 오래된 “블로킹 HTTP” 주석과 단절이 곧
패배라는 설명도 실제 흐름에 맞췄다. 주석은 자명한 대입을 반복하기보다 실패·동시성의
이유를 설명하는 데 사용한다.

| 원칙 | 현재 판단 | 구체적인 경계 |
|---|---|---|
| S — 단일 책임 | 개선했으나 부분 준수 | 계정 UI/서비스/저장/OS 경로 분리. main과 reactor에는 여전히 여러 변경 이유가 남음 |
| O — 확장에 열리고 변경에 닫힘 | 부분 준수 | 캐릭터·테마는 데이터 확장, 두 relay는 공통 검증기. 새 화면·경제 정책은 코드 변경 필요 |
| L — 대체 가능성 | 계약별 검증 필요 | 깊은 상속보다 transport·relay의 동일 wire와 실패 의미가 핵심. 두 relay 통합 검사로 일부 확인 |
| I — 인터페이스 분리 | 개선 | MetaClient에서 파일 저장 제거, AccountScreen은 동작 이름만 반환. SimGame의 공개 가변 상태는 남음 |
| D — 의존성 역전 | 부분 준수 | bot picker·ticket issuer 주입 유지. 검증기는 I/O 없음. 계정 서비스는 여전히 구체 MetaClient에 의존 |

새 화면마다 인터페이스 계층을 늘리는 것이 목표는 아니다. 다음 구조 작업은 main의
상점·봇 보상 흐름을 각각의 서비스/화면으로 나누고, reactor의 입장·룸·경기 수명 경계를
기존 wire 검사 아래에서 점진적으로 분리하는 것이다. 현재 작업에서 코어 전체를 재작성하지 않았다.

## 문서의 현재 기준

실행 안내·운영 문서·Part 구현 교재는 목적이 달라 동일한 분량과 구성을 강요하지 않는다.
Part 시리즈는 같은 제목/시리즈 안내/구현 계약/코드 라벨 규칙을 사용하도록 정리했다.
설명용 라벨의 부가 문장은 라벨 앞의 본문으로 옮겼다. Part 13도 공통 계약 제목 아래에
레퍼런스라는 성격을 명시한다.

- Part 4·9: 제거된 봇 입력 큐 대신 Controller·생각/입력/배치 시간·현행 로스터를 설명한다.
- Part 7·10·12·14: 자기신고/몰수승과 오프라인 인증 캐시를 현재의 서버 입력 검증·입장권으로 교체한다.
- Part 10·11·12·13·17: 서버별 AccountStore, 플랫폼 경로, 원자적 파일 교체와 저장 실패를 반영한다.
- Part 18: 신뢰 경계, 데이터 흐름, 소유권, 입력 제한, 결과 사유, 실패 처리와 수정 지점을 함께 설명한다.
- `scripts/check_part_docs.py`: Part 헤더·구현 계약·코드 라벨·현재 소스 발췌·docs의 로컬 파일 링크를 검사한다. CI에서도 실행한다.

기계 검사로 공통 형식과 현재 소스 발췌의 일치를 확인한다. C/C++ 주석·공백 차이는 허용하고, 노트북은 코드 셀을 읽는다. 본문 설명·체크포인트의 의미는 변경 리뷰에서 대조한다. 과거 모든 발췌의 의미를 자동 검증한 것으로 표현하지 않는다.

## 남아 있는 보안·출시 과제

- 정상 입력을 생성하는 자동 플레이, 일부러 져 주는 담합, PvP의 동일 상대 반복 보상·일일 제한.
- 완료 전에 입력을 끊는 이탈자에 대한 몰수패/제재. 현재는 완결되지 않은 경기를 지급하지 않는다.
- 키 교체 후 이미 승인된 경기의 즉시 세션 회수, 접근 키 자동 만료, 계정 데이터 삭제·보존 정책.
- 접근 키를 훔친 사람이 먼저 키와 복구 코드를 바꾸는 계정 탈취. 신원 확인 없는 파일 복구는 이 상황의 복원 수단이 아니다.
- 새 시뮬레이션 비용을 포함한 실제 ranked 부하·장시간 운영, 네트워크 DDoS·다중 IP 발급 악용.
- Windows 예비 서버와 Windows/macOS 클라이언트의 실제 기기 검수·서명·배포. 웹 게임 포팅도 아직 미구현이다.

가입이 없다는 것은 식별·기록이 전혀 없다는 뜻이 아니다. 토큰, IP 관련 운영 정보,
경기 기록을 어떻게 보관·삭제하는지는 실제 서비스 안내와 운영 정책으로 정해야 한다.
