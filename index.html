한 차시의 흐름

  1. 짧은 복습

    만들어진 코드의 상태와 핵심 개념을 짧게 되짚고 이번 구현으로 연결합니다. 첫 차시에는 생략합니다.

  2. 이번에 만들 것

    어디서 시작하고, 끝났을 때 무엇을 실행할 수 있는지 정합니다.

  3. 필요한 CS

    용어를 정의하고, 지금 구현에서 왜 필요한지 설명합니다. C++를 안다고 운영체제나 그래픽스까지 이미 안다고 가정하지 않습니다.

  4. 함께 구현하고 실행

    파일을 조금씩 추가하고 빌드합니다. 기대 결과와 다르면 어느 단계에서 문제가 생겼는지 확인합니다.

  5. 현재 프로젝트에 연결

    방금 만든 작은 코드가 실제 저장소의 어떤 책임으로 이어지는지 봅니다. 연습용 단순화와 현재 구현의 차이도 표시합니다.

  6. 확인 문제로 마무리

    개념 구별, 결과 예측, 오류 원인, 수정 방법을 묻는 객관식 3~5문제를 풉니다. 하나를 선택하고 확인을 누르면 그 자리에서 정답과 해설을 읽을 수 있습니다.

작게 시작하는 이유

먼저 필요한 만큼 구현하고, 부족한 점을 발견했을 때 구조를 바꿉니다. 파일 분리·추상화·최적화를 처음부터 모두 도입하지 않습니다. 매번 “무엇이 불편해져서 이 설계가 필요한가?”를 확인합니다.

차시는 기존 Part 번호순으로 진행하지 않습니다. 한 차시 안에서도 필요한 절만 연결합니다. 연습은 별도 디렉터리에서 진행하므로 현재 게임의 소스를 초기 코드로 덮어쓰지 않습니다.

강의 코드와 현재 코드를 구분합니다

강의 기준 스니펫은 그 차시의 학습 목표와 구현 순서를 보여 주는 코드입니다. 핵심뿐 아니라 그 단계에서 필요한 세부 구현도 설명합니다. 콘텐츠 수나 파일 배치가 바뀔 때마다 강의 예제를 자동으로 교체하지 않습니다.

현재 코드 레퍼런스는 오른쪽 뷰어에서 확인합니다. 개발용 로컬 학습 서버에서는 현재 작업 폴더를 읽습니다. 다른 서버에 올린 배포본은 그 배포 시점의 소스 스냅샷을 보여 주며 자동 실시간 갱신이 아닙니다. 뷰어에서 자료의 출처와 내용 식별값을 확인할 수 있습니다.

블록·캐릭터 수, UI 수치, 내부 보조 함수 등은 강의와 달라질 수 있습니다. 핵심 책임·의존 방향·입출력 계약이 유지된다면 이 차이는 자연스럽습니다. 해당 계약을 바꾸는 수정에는 관련 강의의 검토가 필요합니다. 이 연결은 줄 번호 대신 파일과 심볼을 기준으로 찾습니다.

02 / 필요한 CS

소스, 실행 파일, 프로세스

읽기 전 예측 · CMake 구성이 성공했다면 실행 파일도 만들어졌을까요? 소스 설정, 빌드 결과, 실행 중인 상태를 나누어 생각해 보세요.

소스는 우리가 작성한 코드입니다. 컴파일러는 전처리된 소스 단위인 번역 단위를 처리해 일반적으로 오브젝트 파일을 만듭니다. 그 안에는 기계어뿐 아니라 함수·변수 이름에 대응하는 심볼과 다른 정의를 참조하기 위한 정보 등이 있습니다.

링커는 오브젝트 파일과 필요한 라이브러리를 연결하고 참조를 해석해 실행 파일을 만듭니다. 함수의 선언을 알아 컴파일에 성공했어도, 호출한 함수의 정의를 연결할 수 없다면 링크에 실패할 수 있습니다.

소스작성한 코드
→
오브젝트컴파일 결과
→
실행 파일링크 결과
→
프로세스실행 중인 상태

파일로 저장된 프로그램을 실행하면 운영체제가 주소 공간 등의 자원을 마련합니다. 이 실행 주체가 프로세스입니다. 소스를 저장하는 것만으로 이미 만든 실행 파일이나 실행 중인 프로세스가 바뀌지는 않습니다.

CMake는 어디에 들어갈까?

CMake는 어떤 소스를 어떤 타깃에 넣고 어떤 라이브러리와 연결할지 기술한 설정으로 빌드 시스템을 생성합니다. 실제 빌드에서는 선택한 빌드 도구가 컴파일러와 링커 등을 실행합니다.

cmake -B build는 구성·생성, cmake --build build는 빌드, ./build/tetris는 만들어진 프로그램 실행입니다. 구성 중에도 컴파일러 확인용 작은 컴파일이 일어날 수 있지만, 프로젝트 실행 파일을 만드는 본 빌드와 구분합니다.

단계 구별구성·빌드·실행을 따로 확인합니다

구성은 어떤 방식으로 빌드할지 준비하는 단계입니다. 빌드는 소스에서 산출물을 만들고, 실행은 만들어진 프로그램으로 프로세스를 시작합니다. 문제가 생기면 마지막으로 성공한 단계부터 찾으세요.

파일 두 개와 세 명령으로 단계 확인하기

작은 실험소스만 바꾸면 무엇이 달라질까요?

출력 문자열을 바꾸고 저장한 뒤, 다시 빌드하기 전에 실행 파일을 실행해 보세요. 이 예제에서는 이전 문자열이 나옵니다. 소스 파일과 실행 파일이 서로 다른 산출물임을 관찰할 수 있습니다. 이어 다시 빌드하고 새 출력을 비교하세요.

03 / 함께 구현

파일 두 개로 시작하기

현재 프로젝트 바깥에 별도 연습 디렉터리를 만드세요. 아래 파일들은 학습용 체크포인트입니다. 완성형 저장소의 같은 이름 파일을 덮어쓰지 않습니다.

tetris-study/
├── CMakeLists.txt
└── src/
    └── main.cpp
강의 기준 코드 · CMakeLists.txt 전체
cmake_minimum_required(VERSION 3.15)
project(tetris LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(tetris src/main.cpp)

add_executable의 첫 인자는 타깃 이름, 뒤는 그 실행 파일에 포함할 소스입니다. REQUIRED ON은 C++17을 지원하지 않을 때 더 낮은 표준으로 조용히 진행하지 않도록 합니다.

강의 기준 코드 · src/main.cpp 전체
#include <iostream>

int main()
{
    std::cout << "tetris project skeleton\n";
    return 0;
}

04 / 현재 프로젝트 연결

작은 빌드 파일은 어디로 자랄까?

완성형 저장소의 CMakeLists.txt를 열고 다음 세 이름만 찾아보세요. 전체 옵션을 한 번에 이해할 필요는 없습니다.

TETRIS_SIM_SOURCES

TETRIS_GAME_COMMON

add_executable(tetris ...)
플랫폼별 구현까지 모아 게임 실행 파일을 만드는 지점입니다.
목록과 타깃은 다릅니다

TETRIS_SIM_SOURCES는 소스 목록입니다. 이 변수를 선언하는 것만으로 독립 라이브러리가 생기지는 않습니다.

게임 보드의 행·열은 화면의 x·y로 어떻게 바뀔까요? 규칙과 그림을 왜 분리할까요?

배울 개념

연속 메모리와 바이트 크기 → VBO·VAO와 정점 형식 → clip 좌표와 NDC → 보간·래스터화 → 텍스처·블렌딩 → 비동기 실행과 버퍼 교체로 이어집니다.

기본 경로를 만든 뒤 배칭, 이미지, CPU 글리프 래스터화와 GPU 아틀라스, 해상도별 캐시, UI 좌표와 애니메이션을 붙입니다. 드라이버나 OS 자체를 구현하는 과정과는 범위를 구분합니다.
